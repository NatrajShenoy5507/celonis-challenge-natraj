# Part D — Performance and load testing

## Objective and scope

The performance question is whether OMS-to-Analytics synchronization remains responsive and reliable as concurrency grows. No authorized OMS or Analytics performance environment is available, so the executable framework targets only the bounded, localhost Node.js mock in `performance/`. Mock timings and capacity are not predictions of production behavior.

## Baseline, deploy, compare

Record a low-concurrency fixed-iteration baseline before a real deployment, deploy through the authorized release process, then repeat the same profile and settings afterward. For a like-for-like comparison, keep the environment and infrastructure conditions, workload profile, VU or arrival-rate configuration, duration, endpoint request distribution, dataset characteristics, thresholds, and monitoring approach equivalent. Compare p50/p95/p99 latency, throughput, error rate, resource utilization where available, and end-to-end synchronization behavior where observable.

Repeat runs when practical and investigate differences rather than attributing them automatically to the deployment. A single better or worse result does not prove a deployment caused an improvement or regression. The local `pre` and `post` labels are demonstration run labels only.

## Workload design and endpoint selection

Start by identifying frequently accessed APIs from customer usage and monitoring, then include business-critical operations even if they are less frequent. Map representative customer workflows and their request sequences; estimate normal traffic, peak traffic, and expected growth; and model a realistic request distribution rather than applying equal load to every endpoint.

For OMS-to-Analytics flows, prioritize synchronization-related operations such as order creation, confirmation, shipment, delivery, cancellation, and return processing where corresponding APIs exist. This list describes business operations, not actual Celonis endpoints. Base endpoint selection and traffic distribution on production traffic, monitoring information, or agreed business expectations; none of those production inputs are available for this local demonstration.

## Load modelling and ramp-up strategy

| Scenario | Workload design | Evidence to evaluate |
|---|---|---|
| **Baseline** | Low concurrency and fixed iterations using `shared-iterations`. | Reference latency percentiles, throughput, and errors. |
| **Load** | Gradually ramp to expected operational traffic, sustain the agreed peak, then ramp down. | Latency, throughput, errors, downstream processing, and recovery. |
| **Stress** | In an authorized environment, increase beyond expected peak within agreed safety limits. | Saturation point, graceful degradation, failure behavior, and recovery. |
| **Soak** | Sustain an agreed workload for an extended duration. | Memory/resource growth, leaks, queue accumulation, and gradual latency degradation. |

The practical sequence is to establish a low-concurrency baseline with predefined iterations, gradually ramp load, exercise normal expected traffic, then peak expected traffic, and optionally test approximately 30% above the agreed peak to evaluate capacity headroom. This 30% is a proposed scenario, not a universal performance requirement; agree the peak and headroom with the business/service owner. Gradually ramp down and observe recovery, including whether errors or backlogs drain.

Use the existing `.env` settings and predefined profiles where they represent the agreed scenario. Do not silently alter the configured VU counts, iterations, durations, or thresholds. `ramping-vus` models concurrent users; it does not promise a request rate. Consider `ramping-arrival-rate` when the requirement is explicitly expressed as requests per second or arrival rate. The current short local stress and soak profiles demonstrate workload setup only; they are not enterprise-scale stress or soak tests. Meaningful pre/post comparisons require equivalent test conditions.

## Enterprise-Scale Workload Model

For a real, authorized environment, model the volume and distribution from production traffic or agreed business requirements—not invented Celonis figures. Establish expected daily and peak order volumes, average and peak ingestion rates, and the number of events generated by each order lifecycle. Include concurrent order creation and lifecycle updates, realistic endpoint/request distributions, and bursty batch ingestion. Account for event-log growth, retries during transient downstream failures, queue growth, and how quickly backlog recovers after a burst.

Keep these measures distinct:

1. **Orders in the test dataset:** total business orders represented.
2. **API requests per second:** request arrival rate at the tested API.
3. **Lifecycle events ingested per second:** downstream event-processing rate; one order may generate multiple events.

They are related but not interchangeable. A proposed run at approximately 30% above observed peak traffic can assess extra capacity headroom, provided the peak and test safety limits are agreed. The local mock does not reproduce enterprise order volumes, burst capacity, queue behavior, or production integration capacity.

## Measurements and oracles

The acceptance measurement is the mock HTTP sync response: p50, p95, p99 latency, sync request count, completed iterations/second, and failed acceptance checks. These are primarily client-side k6 measurements. Also review HTTP error rate, timeouts, connection failures, and HTTP 5xx/429 responses when present. Configured thresholds are evaluated by k6 and shown separately from execution errors. Optional, sampled status polling records completion observation time and completion success separately; the observation is bounded by the polling interval and limit, not precise backend processing lag.

Where infrastructure telemetry is available, correlate application results with CPU and memory utilization, garbage collection or memory pressure, active threads/thread-pool use, database connection-pool use, network utilization, queue depth, and downstream processing capacity. These infrastructure signals generally require separate monitoring or application telemetry; the current mock does not implement them.

## Performance error investigation

Investigate increasing latency, HTTP 500/502/503/504 or 429 responses, timeouts, connection failures, failed checks, resource saturation, thread-pool or database-pool exhaustion, growing synchronization backlogs, processing delays, and dropped or duplicated events. Correlate k6 timings and response/error evidence with server logs, infrastructure metrics, and application telemetry where available. Treat these as investigation signals, not proof of a specific component cause.

## OMS-to-Analytics end-to-end validation

HTTP 202 means the mock accepted a request. It does **not** prove Analytics ingestion or downstream completion. On a real authorized system, also inspect queue depth, ingestion lag, backlog drain time, duplicate/drop rates, and run Part C-style reconciliation for missing, duplicate, orphaned, incorrect-amount/currency, temporally invalid, and lifecycle-inconsistent events.

For example, if OMS sends 1,000 orders and the API accepts them but only 850 are eventually represented in Analytics, that is an integration/data-consistency failure even if API latency is acceptable. In an authorized real environment, measure end-to-end synchronization lag, queue depth and backlog growth/drain or recovery time, event-processing throughput, missing/dropped and duplicate events, referential integrity, amount/currency correctness, and lifecycle/timestamp consistency. Reuse the Part C deterministic reconciliation approach when corresponding source and target exports are available. The local mock only simulates acceptance and asynchronous status; it does not validate real Celonis ingestion.

## SLI/SLO targets

All numeric values below are **illustrative proposals**, not official Celonis requirements. Agree service-specific SLOs and telemetry with stakeholders before making release decisions.

| SLI | Illustrative proposed SLO |
|---|---|
| API p95 acceptance latency | `<500 ms` |
| API p99 acceptance latency | `<1,000 ms` |
| API error rate | `≤1%` (matches the current k6 demo threshold of `0.01`) |
| Request throughput | Sustain the agreed peak request rate; no numeric rate is specified without a business workload. |
| Event-ingestion throughput | Sustain expected event arrival without unbounded backlog growth. |
| End-to-end synchronization lag | Within an agreed business delay; no numeric target is supplied. |
| Data integrity | No missing, orphaned, or unintended duplicate events in fully processed batches. |
| Backlog recovery | Drain within an agreed recovery window after traffic returns to normal; no numeric target is supplied. |

These cover distinct oracles: **HTTP acceptance latency** measures how quickly the API accepts a request; **downstream completion** measures when its events are processed; **data correctness** is checked by reconciling OMS and Analytics evidence. The current k6 thresholds are `K6_ACCEPT_P95_MS=500` and `K6_ACCEPT_ERROR_RATE=0.01`; the p99 and downstream targets require appropriate real-system telemetry and are not currently enforced by this mock profile.

## Configuration and execution

The isolated `performance/.env` controls target, VUs/iterations/stages, thresholds, mock delay/capacity, and optional completion sampling. The runner defaults to loopback and blocks non-local targets unless `K6_ALLOW_REMOTE=true`; that opt-in does not grant authorization. Never target a public demo site. Follow the PowerShell runbook in [`performance/README.md`](./performance/README.md). Machine-readable k6 summaries and comparison Markdown are written to the ignored `performance/results/` directory.

The comparator requires the same profile, target host, and workload settings. A mismatch is reported and prevents a direct comparison. The comparison is descriptive, not proof of a deployment effect or statistical significance.

## Why k6 and runnable stub

k6 was selected for JavaScript-based, version-controlled scenarios; fixed-iteration and ramp-up workloads; configurable thresholds; CLI/CI execution; and machine-readable output for comparison.

The optional runnable stub under `performance/` demonstrates k6 execution and result collection against the controlled localhost mock API. Its workload values come from `.env`; use [`performance/README.md`](./performance/README.md) for setup and commands. Ensure `K6_TARGET_URL` points to the local mock: the current sample configuration names a public host while remote access is disabled, so the safety guard will reject it. The stub does not benchmark Celonis or an enterprise system. A full-scale performance run is **not required** for this challenge.

## Limitations and AI-first workflow

The local mock has no real Celonis endpoint, database, queue, or enterprise ingestion pipeline. Its bounded state and configurable delay exist to exercise the framework only. No remote load was run. AI/Copilot assisted implementation and test design; the human reviewer remains responsible for workload realism, authorized execution, metric interpretation, and release decisions.
